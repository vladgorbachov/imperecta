# Product Matching — план (roadmap item 3, старт Rust data-ops слоя)

Цель: сгруппировать идентичные товары разных магазинов в кросс-шоповые
группы (`match_group_id` на `dim_product`), чтобы открыть P6 (сравнение цен
по магазинам) и лечь фундаментом Rust data-ops слоя.

## Сравнительный анализ алгоритмов (правило optimal-algorithms)

| Кандидат | Сложность | Многоязычность | Вердикт |
|---|---|---|---|
| Пары по trgm-похожести всего пула | ~O(n²) кандидатов, planner-ловушки | плохо: один товар в 10+ языках делит мало токенов | отклонён как первичный |
| MinHash/LSH по шинглам тайтла | O(n) | плохо на сырых тайтлах; хорошо на `title_en` | **M2** — поверх title_en, когда enrichment заполнит |
| Детерминированный блокинг (brand_token, model_code) | O(n), инкрементальный | модельные коды ASCII и языко-инвариантны | **выбран для M1** |
| GTIN/EAN точный | O(n), максимум точности | идеален | данных 0% сегодня; зарезервирован method='gtin' |

Точность M1 охраняется требованием «бренд И код»; полнота ограничена
(товары без кода → M2). Ложный мэтч хуже пропущенного: пропущенный чинится
следующим проходом, ложный портит сравнение цен.

## M1 (этот слайс) — brand+model блокинг

Сигнатура из `name_normalized` (Rust `matching.rs` + Python reference,
фасад как у pricing):

- токены `[a-z0-9]+` из lowercase-имени;
- **юнит-токены** (`256gb`, `20mm`, `1080p`, `2x`, `10szt`…) → атрибуты,
  никогда не модельный код;
- **модельный код**: смешанный alnum-токен len≥4 (`sfd950ss`, `gxt492w`),
  плюс склейки соседей alpha+digit (`galaxy`+`s24`→`galaxys24` — тот же
  приём, что numeric_edge_tokens в listing_page), плюс чисто цифровые
  len 5–9 как слабый код (артикулы стилей);
- **бренд**: токен из известных брендов (dim_brand, 253) — conf 0.90;
  иначе первый алфавитный токен len≥3 — conf 0.75;
- нет бренда или нет кода (мусорные слаги `pb00613262.html`, чистые цифры)
  → `unmatched`.

`match_group_id = uuid5(NS_MATCH, brand + "|" + сильнейший код)` —
детерминирован ⇒ инкрементальные прогоны сходятся без таблицы групп и
без координации (permanent-pool-совместимо).

Хранение: 3 колонки на `dim_product` (без edge-таблицы — членство 1:1,
на один join меньше на read-path): `match_group_id uuid`,
`match_method varchar(16)` ('brand_model' | 'unmatched'; резерв 'gtin',
'title_sim'), `match_confidence numeric(3,2)`. Индексы: частичный по
group_id, частичный pending (`match_method IS NULL AND is_active`).

Запись: gate-дверь `dim_product.product_match` (SCRAPE_UPDATE_ALLOWLIST),
пайплайн `exec_write_records` чанками по 100.

Beat: `product_match_tick` */10 мин, 10 000 продуктов/тик → полный пул
~1.75M за ~30 часов; далее тик подъедает только новые продукты.

## M2+ (по мере данных)

- `title_sim`: LSH/скоринг по `title_en` внутри блока (product_type_en,
  brand) для товаров без модельного кода. Скоринг-функция уже в M1-модуле.
- `gtin`: когда PDP-скрейпы начнут заполнять sku_universal/mpn — высший
  приоритет, перезаписывает brand_model.
- Re-sweep: bulk-сброс `unmatched` → NULL после волн harvest-переименований
  (реальные тайтлы вместо слагов) — ручной SQL или месячный cron.
- Конфликт атрибутов внутри группы (256gb vs 512gb) — понизить
  confidence / расщепить группу вторым проходом.
- P6 read path (список офферов группы с ценами) — целевой дом: Rust
  data-ops сервис со своими gate-дверьми; до его появления временный
  FastAPI-эндпоинт можно не строить, фронт ждёт по договорённости.

## Rust data-ops слой — траектория

M1 кладёт матчинг-ядро в `rust_core` (PyO3) — оно переедет в standalone
data-ops сервис вместе с read-path (поиск p95, retention-union чтения,
P6 API). Контракты проектируем так, чтобы сервис читал те же таблицы и
писал через те же gate.exec_write двери (HMAC языко-агностичен).
